# Lifecycle fixtures

A fresh install of the current tree creates only the new schema and marks every patch complete, so a lifecycle fixture's `prepare()` step (the code that seeds legacy state before the first migrate) must reconstruct the schema state for the release immediately before the migration under test. For a rename or retype, recreate the old shape (the old `DocType` record and its table, or the old column) with direct writes and DDL, load legacy rows into it, and assert it exists before the first migrate. For an additive field tested in release N, drop the new column and clear the DocType's `migration_hash` so the first migrate re-imports the JSON and performs the real `ADD`. For a staged field tested in release N+1, keep the column that release N introduced, but remove any manual index that `after_install` already created before seeding legacy values; then verify the N+1 backfill and index installation against that prior-release state. In particular, a staged non-null unique field must start with duplicate legacy/default values and no new unique index, so the test proves the backfill makes values distinct before the migration installs the index. Never let a fresh-install index prevent the legacy rows from being seeded. A Single DocType has no table: recreate the old `(doctype, field, value)` row in `tabSingles`, delete any new-field row, and assert the migrated business value. For a DocType rename, first remove the new `DocType` record and table, then assert only the old one exists, because the rename guard throws when both exist; otherwise the guards skip and the test passes without migrating anything.

For column-backed field renames and retypes, restore the preceding release's field metadata and column definition. If the migration introduces a replacement column, drop the new column left by the fresh install before recreating and populating the old one; for an in-place retype, restore the old column type instead. Clear the parent DocType's `migration_hash` so model sync imports the current JSON and executes the real `ADD` or `ALTER`. Before the first migrate, assert the old metadata, column definition, and legacy values exist, and any replacement column is absent; afterwards assert the new schema and migrated business values. Recreating only the old column leaves a hybrid schema and can miss failures in schema sync.

For existing fields being tightened, lifecycle `prepare()` must restore the preceding release's metadata and database state: keep the field optional or non-unique, remove any new unique index before seeding duplicate legacy values, and seed empty values for requiredness. After restoring the old metadata, clear the parent DocType's `migration_hash` so model sync reimports the current JSON; in particular, the fixture for the release that enables `reqd` must start with it disabled and verify that migration enables it. Cover each staged transition with populated rows, assert cleanup/backfill preserves the intended business values, and verify the constraint or `reqd` is enabled only after the data is valid. Assert duplicate writes fail once the unique constraint is installed, empty saves fail once `reqd` is enabled, valid writes succeed, and forced patch reruns preserve migrated values.

Also cover a direct upgrade from populated pre-cleanup data to the latest release for staged uniqueness, including skipped intermediate releases and a restored/offline database. Reconstruct the older metadata and schema, remove the new index, seed duplicates, remove cleanup Patch Logs, and clear the DocType's `migration_hash` so real model sync runs. While that upgrade path is supported, assert migration succeeds, business values are preserved, cleanup precedes manual constraint installation, and forced reruns remain safe. Before promoting to the DocField flag, test that a pre-cleanup database is rejected by the prerequisite check before model sync, while a database that completed the cleanup release upgrades successfully. Retain the ordinary staged lifecycle cases too.
