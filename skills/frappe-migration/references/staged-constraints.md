# Staged constraints

Read this when an additive change hits a schema exception, or when an existing field becomes unique or required.

Both staged uniqueness recipes below must satisfy [Promoting staged uniqueness](#promoting-staged-uniqueness) before enabling the DocField `unique` flag in a later release.

## Additive schema exceptions

A new field with a default on an existing Single DocType is one schema exception: sync stores no `tabSingles` value and defaults apply only when the Single has no stored values at all, so established sites read `None`. Backfill a business default with an idempotent data patch and test it on a populated site. A new `unique` field is another: model sync adds it as `ADD COLUMN ... UNIQUE` with its default, which fails on a populated table for NOT NULL types (`Check`, `Int`, `Currency`, `Float`, `Percent`) or any field with a default. If the field is nullable with no default (for example `Data` or `Link`), sync's `ADD COLUMN ... UNIQUE` succeeds on a populated table and previous-release workers insert `NULL`, which a MariaDB unique index allows more than once, so declare `unique` in the same release. Otherwise ship it in release N without `unique` and with nothing relying on its uniqueness yet, because controller validation alone is a check-then-insert race; previous-release workers insert the column default, so in release N+1, after no pre-N writer can run, backfill distinct values, check for duplicates, and install an idempotent manual unique index from the patch, `after_install`, and `after_migrate` (sync drops a unique index the DocField does not declare). Set the DocField `unique` flag only in a later release, and cover the ordering with a populated lifecycle case. If the deployment stops every previous-release worker before migrate, N and N+1 can be one release. A new `reqd` field on a populated DocType without a usable default is a third exception: sync adds the column empty and existing documents then fail mandatory validation on save. Ship it optional in release N with every server writer populating it; in release N+1, after no pre-N writer can run, backfill it in an idempotent `[post_model_sync]` patch, set `reqd`, and verify populated legacy rows. As with `unique`, N and N+1 can be one release only if the deployment stops every previous-release worker before migrate.

## Tighten an existing field

- **Tighten an existing field** (non-unique to unique, optional to required): stage the change across releases, with populated lifecycle coverage for each transition.
  - **Unique:** in release N, keep `unique` disabled, update every writer to produce distinct values, and keep all code independent of the uniqueness invariant; controller checks alone still race. In release N+1, after all old writers that can create duplicates are drained and cannot return through rollback, clean legacy duplicates with an idempotent data patch, verify no duplicates remain, then install the database constraint. Keep the DocField `unique` flag disabled during that cleanup release so model sync cannot install the constraint before the data patch. Install an idempotent manual unique index from the patch, `after_install`, and `after_migrate`; enable the DocField flag only in a later release. Code may rely on uniqueness only after cleanup and database enforcement succeed.
  - **Required:** in release N, keep the field optional while updating every writer to populate a usable value. In release N+1, after all old writers that can omit it are drained and cannot return through rollback, backfill existing empty values with an idempotent data patch and verify every existing row has a usable value. Only then enable `reqd` in a later release.

## Promoting staged uniqueness

For every staged unique field (new, renamed, or existing), keep the DocField `unique` flag disabled and retain the cleanup patch and manual index hooks while direct upgrades from pre-cleanup sites, offline copies, or restored backups remain supported. A later release date does not prove that a source database ran cleanup: model sync installs a declared unique constraint before `[post_model_sync]` patches, so retaining a post-sync cleanup patch alone cannot protect a skipped-release upgrade.

Enable the DocField flag only after every supported source database has completed cleanup and constraint installation. Enforce that prerequisite before model sync with a database migration-state check, including for restored backups; reject an older database with instructions to upgrade through the cleanup release first, before sync can attempt the unique constraint. Keep the flag disabled if direct upgrades from those older databases must continue to succeed. This prerequisite supplements the existing writer-draining and staged rollout rules.
